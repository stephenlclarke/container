# Pull request 179: avoid prewarming block-backed containers

## Summary

- Make dedicated background prewarming ineligible when a container
  configuration contains a block mount.
- Preserve prewarming for mount-free and VirtioFS-only dedicated containers.
- Extend the focused eligibility regression across named-volume, raw-block,
  and VirtioFS mount shapes.

Tracking pull request: [`stephenlclarke/container#179`](https://github.com/stephenlclarke/container/pull/179).

## Functional reason

Dedicated prewarming boots a VM before the user starts the container. For
block-backed volumes that speculative VM owns the Virtualization.framework
storage attachment, preventing another created container or a Compose lifecycle
helper from bootstrapping with the same volume. Deferring the boot until
explicit start preserves correct shared-volume ownership.

## Evidence

- The focused `dedicatedPrewarmEligibility` regression passed from a clean exact
  build and with `--skip-build`.
- A signed release-mode candidate embedded the exact implementation commit.
- Strict Docker Compose lifecycle-hook parity passed end to end with the fixed
  candidate, covering inherited anonymous and named volumes, scale, restart,
  stop/start, failure gating, and one-off run hooks.
- The earlier raw reproduction failed when two created containers shared a
  named volume and succeeded after deleting the prewarmed source container,
  isolating attachment ownership as the cause.

## Compatibility and risk

No CLI or public API changes. Block-backed dedicated containers lose
speculative warm-start latency until prewarming can prove exclusive storage
ownership; other eligible dedicated containers retain the optimization.
